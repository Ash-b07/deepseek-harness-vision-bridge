# 从 shim 到独立视觉编排：一次约束驱动的问题解决

## 一句话摘要

我把一个“给纯文本 DeepSeek 加看图能力”的原型，迭代成了主模型与视觉模型独立选择的 Harness 插件；过程中依次解决了 UI 污染、图片准入、只读请求、递归调用和能力证据冲突，并为每个关键边界建立了可回归验证。

## 1. 我真正要解决的不是“调用一个视觉模型”

调用多模态 API 并不难。真正的目标包含一组互相制约的条件：

1. 主模型继续使用 DeepSeek，保留它的推理、工具和上下文；
2. 图片只交给用户明确选择的视觉模型；
3. 用户不应为了上传图片而切换到一个伪造的主模型 Provider；
4. 不重复维护 API Key、base URL 和重试链路；
5. 会话历史、模型选择和工具协议不能被破坏；
6. 方案必须能安装、验证和回滚。

因此，这不是一个单点 API 集成，而是 UI、Host、模型运行时和协议能力共同参与的编排问题。

## 2. 1.0 为什么能用，却不是正确的长期交互

1.0 注册了 `vision-bridge` shim Provider。它对外声明图片能力，在内部让视觉模型生成描述，再把纯文本转给 DeepSeek。

这条路证明了数据流可行，却产生了明显的产品债务：

- 主模型选择器出现额外的 `vision-bridge` 分组；
- 用户必须在“真实 DeepSeek”和“桥接后的 DeepSeek”之间手动切换；
- Provider 身份同时承担主模型选择与视觉编排，两个概念被混在一起；
- 每轮扫描历史图片，容易重复识别并放大 429。

我的判断是：不能继续美化 shim，而应重新划分责任。

## 3. 从参考方案中提取结构，而不是照搬绑定

`deepseek-harness-studio` 提供了一个关键启发：视觉能力可以是独立入口，而不是主模型 Provider。

我借鉴的是结构：

- 一个独立视觉选择点；
- Host 在图片准入阶段知道视觉增强是否开启；
- 模型目录暴露模态能力；
- 图片先变成结构化视觉观察，再交给主模型。

我没有照搬固定模型或固定服务商。2.0 的视觉路由来自 Harness 自己的模型目录，因此继续复用现有 Provider、凭据、重试和计费链路。

## 4. 第一层阻塞：插件还没运行，图片已经被 Host 拒绝

最初很容易误判为“在 `llm/stream` 里处理图片就够了”。真实链路却是：

```text
用户上传图片
  → Host 检查当前主模型 inputModalities
  → 纯文本模型被拒绝
  → 插件的模型流钩子根本没有机会运行
```

我把问题定位为准入顺序，而不是模型调用失败。对应解法是一个刻意收窄的 Host 补丁：

1. 视觉增强开启时，放行当前会话接收图片；
2. 模型目录 API 返回 `inputModalities`，供独立选择器过滤；
3. 不改主模型选择，不注册伪 Provider；
4. 用 rc.6 精确代码签名防止在未知宿主版本上猜测性修改；
5. 保留原文件备份并提供显式回滚。

这个决策体现的原则是：只修改阻塞插件发挥作用的最小宿主边界。

## 5. 第二层阻塞：测试通过，实机却报只读属性错误

第一版自动编排在处理完图片后执行：

```js
options.messages = messages;
```

实机立即暴露错误：

```text
Cannot assign to read only property 'messages' of object '#<Object>'
```

我没有用解冻、强制覆盖或修改 Harness 不变量来绕过错误，而是继续追踪运行时契约。证据显示：Agent Loop 构造的模型请求会被深度冻结；`llm/stream` 监听器只能读取它，不能重写模型可见历史。

最终修复：

```text
冻结的原请求（保持不变）
  → 视觉模型生成 observation
  → 创建保留 provider/model/signal 等字段的克隆请求
  → 克隆请求只携带文本 observation
  → 重新进入同一个 LLM runtime
  → 原主模型继续回答
```

这既服从 Harness 的不可变请求契约，也保留了原模型路由。

## 6. 修复又引入了一个潜在问题：内部调用递归

克隆请求重新进入 `ctx.llm.stream()`，意味着同一个全局视觉钩子还会再看到它。如果只依赖“已经没有图片”，当前代码也许能退出，但未来消息形态变化时容易重新触发。

我增加了显式的一次性保护：

- 克隆请求对象放入 WeakSet；
- 钩子只对该对象绕过一次编排；
- WeakSet 不延长请求生命周期；
- 回归测试让视觉调用和主模型调用真实地再次经过同一中间件；
- 断言最终只有一次视觉适配器调用和一次主模型适配器调用。

这不是为了让当前测试“刚好通过”，而是把递归边界写成可执行契约。

## 7. 第三层判断：模型声明支持图片，等于官方 API 支持吗？

[anomalyco/opencode#26775](https://github.com/anomalyco/opencode/issues/26775) 提供了重要证据：OpenCode v0.99.1 的 `deepseek-v4-flash` 条目声明 `input: [text, image]`，但 OpenAI Chat 协议只允许 text，因此图片在网络请求发出前被拒绝。

如果只看这一条证据，很容易得出“模型本身有视觉，只是协议拦了”的结论。我继续查了更靠近服务端的官方资料：

- DeepSeek [Chat Completions API](https://api-docs.deepseek.com/api/create-chat-completion/) 把 user content 定义为文本字符串，没有 `image_url` 结构；
- DeepSeek [Anthropic API 兼容表](https://api-docs.deepseek.com/guides/anthropic_api/) 明确把 `type=image` 标为不支持；
- DeepSeek [GitHub Copilot 集成](https://api-docs.deepseek.com/quick_start/agent_integrations/github_copilot/) 把 V4 描述为 text-only，图片由其他视觉模型代理。

所以更严谨的结论是：

| 层级 | 当前证据 |
|---|---|
| OpenCode 模型元数据 | 某版本条目声明 text+image |
| OpenCode OpenAI Chat 协议 | 客户端只允许 text |
| DeepSeek 官方公开 API | 当前文档仍是 text-only / image not supported |
| 本插件策略 | 不押注未证实的原生视觉；通过独立 VLM 提供确定性桥接 |

这里体现的是证据优先级：配置声明是线索，不是服务端能力证明。

## 8. 我如何验证“解决了”，而不是只验证“能运行”

验证被分成五层：

1. **纯函数层**：递归图片检测、提示构造、缓存键和失败归一化；
2. **Harness 合约层**：工具 Schema、附件解析、模型流块收集；
3. **故障回归层**：深度冻结请求、同一路由绕过、内部调用防递归；
4. **Host 集成层**：签名检查、幂等安装、设置暴露、`inputModalities` 返回；
5. **产品体验层**：主模型列表无 `vision-bridge`、独立视觉入口只显示图片模型、设置跨会话持久化。

发布前还执行了语法检查、敏感信息扫描、本机 HTTP 200 检查，以及 GitHub Actions 的 Node.js 20/22 测试。

## 9. 最终结果

2.0 达成了最初的产品目标：

- 主模型选择器保持干净；
- 视觉模型成为独立且持久化的选择；
- 图片自动转为结构化观察；
- 主模型 Provider、模型和推理参数不改变；
- 冻结请求保持不可变；
- 关键失败都有回归测试；
- Host 修改可检查、可重复安装、可回滚；
- 文档保留了错误、证据冲突和决策过程。

对我来说，这次迭代最有价值的不是“接入了一个 VLM”，而是建立了一套可复用的方法：先分层定位约束，再选择最小修改面；遇到反例时修正假设；最后把关键边界固化为测试和公开证据。
